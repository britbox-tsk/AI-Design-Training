# Design Sandbox

This is a **learning sandbox** for the design team. Nothing here ships to production. The goal is to practice building prototypes and coded components with AI, using our design system as the guide. Favor clarity and experimentation over polish or performance.

The person working with you is a designer, not necessarily a developer. When you make a change, briefly explain what you did and why in plain language. If a concept (props, state, hooks) is likely new to them, explain it in one or two sentences.

## Stack

- React + TypeScript, built with Vite
- Tailwind CSS v4 (tokens defined via `@theme` in generated CSS)
- Storybook for component documentation (not in the starter yet — added in Module 7)
- Style Dictionary for turning Figma tokens into CSS

## Commands

- `npm install`: install dependencies
- `npm run dev`: start the prototype at http://localhost:5173
- `npm run tokens`: regenerate `src/styles/tokens.css` from `tokens/tokens.json`
- `npm run build`: production build (use to check for errors)
- `npm run storybook`: start Storybook at http://localhost:6006 (available once Module 7 adds Storybook — not in the starter)

## Project structure

- `tokens/`: design tokens exported from Figma (source of truth). Do not hand-edit generated files.
- `src/styles/tokens.css`: GENERATED by `npm run tokens`. Never edit directly.
- `src/components/`: reusable components, one folder each (`Button/Button.tsx`, `Button.stories.tsx`)
- `src/prototypes/`: one folder per prototype. Prototypes compose components from `src/components/`.
- `docs/`: notes on the token pipeline and the learning modules

## Design system rules

These matter most. Follow them even if a shortcut would be faster.

1. **Never hardcode design values.** No hex colors, pixel spacing, font sizes, radii, or shadows in components. Use token-based Tailwind classes (e.g. `bg-brand-primary`, `p-4`, `rounded-md`) or CSS variables (e.g. `var(--color-brand-primary)`).
2. **If a needed token doesn't exist, stop and ask.** Suggest the closest existing token, or propose a new token name, but do not invent a raw value.
3. **Reuse before creating.** Check `src/components/` for an existing component before building a new one. Compose existing components rather than duplicating styles.
4. **Match Figma, not your assumptions.** When a Figma link is provided, read it with the Figma MCP tools (frames, variables, component properties) rather than guessing from a description. If the Figma design and our tokens disagree, point out the discrepancy rather than silently picking one.
5. **Token naming:** `category-role-variant`, lowercase, hyphenated (e.g. `color-text-muted`, `spacing-4`). TODO: replace with our actual convention.

## Component conventions

- One component per folder: `ComponentName/ComponentName.tsx`, `ComponentName.stories.tsx`, and an `index.ts` export.
- Typed props with a short comment on each non-obvious prop.
- Mirror Figma variant names in prop names and values where possible (e.g. Figma `Size=Large` becomes `size="large"`).
- Every component should handle: default, hover, focus-visible, disabled, and (where relevant) loading and error states.
- Every component gets a Storybook story covering each variant and state. Use Storybook `args` and `argTypes` so variants are controllable.
- Keep components small and readable. Prefer plain props over clever abstractions.

## Accessibility

- Use semantic HTML (`button`, `nav`, `label`, headings in order) before reaching for ARIA.
- All interactive elements must be keyboard operable with a visible focus style.
- Form inputs need associated labels; errors must be announced and not rely on color alone.
- Maintain WCAG AA contrast. If a token pairing fails contrast, flag it.
- Run the Storybook a11y addon check on new components and mention any violations.

## How to work with me

- **For anything bigger than a small tweak, propose a plan first** and wait for approval before editing files.
- Make changes in small steps so the diff is easy to review.
- Use realistic placeholder content (plausible names, dates, and data), not "Lorem ipsum" or "Test 1".
- Don't install new dependencies without asking first and explaining why.
- Don't delete files or run destructive commands (`rm -rf`, `git reset --hard`, force pushes) without explicit confirmation.
- After changes, tell me how to see the result (which URL or Storybook story to open).
- If a request is ambiguous, ask one clarifying question rather than guessing.

## Git

- Commit working states often with short, descriptive messages so we can always roll back.
- Work on a branch for each prototype or experiment (`proto/checkout-flow`).
- Never commit secrets, tokens, or `.env` files.
